# 不做 BFF，页面聚合交给前端 + 批量状态接口

页面聚合由前端完成，网关只做路由与鉴权。前端对帖子详情页并发发起 3 个请求（内容+计数快照 / 评论列表 / 批量查询多目标的"我赞过没·收藏没"），自行拼装。不设 BFF，也不允许服务间同步调用做读路径编排。理由是：BFF 要多一个进程和一层独立契约，而本系统只有一个页面需要跨三个服务聚合；把 N+1 消掉之后，前端并发请求的成本远低于维护一个聚合层。而服务间同步编排的爆炸半径不可控——一条慢链路会顺着 Feign 传到最后一道。

## Considered Options

- **BFF 聚合层**：前端契约更干净，但多一处故障点，且作品集里很难讲清必要性。
- **content-service 内部 Feign 编排读路径**：把跨服务延迟和故障直接叠在核心页面上，最差选项。

## Consequences

- **写路径允许一次同步跨服务调用**（如校验被 @ 的用户是否存在），但读路径禁止。这个区分必须显式写在代码注释里，否则会被后人抹平。
- 前端需要知道各服务的路径前缀，服务边界因此对前端可见——这是刻意的取舍。
- 所有接口用 OpenAPI 统一描述，否则契约碎成 7 份。
- 若未来出现需要跨 4 个以上服务聚合的页面，重新评估是否引入 BFF。
