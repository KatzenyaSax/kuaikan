# 计数一致性：强一致、最终一致、对账的边界

点赞数、收藏数、评论数看起来是同一类东西，但它们的**写入者**和**一致性要求**完全不同。
这份 ADR 把边界固定下来，因为"哪个计数能慢、慢多久、错了谁来修"一旦散落在代码里，
就再也说不清，而后面每一层（通知、排行、搜索）都会依赖这个边界。

## 三类计数

| 计数 | 唯一写入者 | 一致性 | 实现 |
|---|---|---|---|
| `post.comment_count` | content | **强一致** | 评论写入/删除的同一本地事务 |
| `comment.reply_count` | content | **强一致** | 同上 |
| `community.member_count` | community | **强一致** | 加入/退出的同一本地事务（P2.2 已实现） |
| `post.like_count` / `post.favorite_count` | content | **最终一致，滞后 ≤5s** | 消费 interaction 的事件 |
| `comment.like_count` | content | **最终一致，滞后 ≤5s** | 同上 |

### 为什么评论数能强一致，点赞数不能

评论的**事实**（`t_comment`）和**计数**（`t_post.comment_count`）都在 content 的库里，
同一个本地事务就能保证两者一起成功或一起失败。没有跨服务，就没有最终一致的必要。

点赞的事实（`t_interaction`）在 interaction 的库里，计数在 content 的库里。
要强一致只有一条路：**点赞时同步调用 content 改计数**。这条路被否决，理由是可用性：

```
interaction ──同步──> content
```

content 挂掉时全站点不了赞，而且 content 写库慢会直接拖慢点赞响应。
点赞是最高频的写操作，把它绑在另一个服务的可用性上不可接受。

**这与 ADR 0009 是同一个判断**：能用"异步 + 补偿"的地方，不要用"同步依赖"。

## 为什么必须是 outbox，而不是"写完直接发 MQ"

```
❌ 直接发：
   t_interaction 提交成功 → 发 MQ 失败（网络/ broker 重启）→ 事件永久丢失 → 计数永久错

✅ outbox：
   同一本地事务里写 t_interaction + t_outbox
   → 事务提交 = 事件一定被记住
   → 后台投递，失败重试直到成功
```

`t_outbox` 是"待办事项表"，不是消息队列。它解决的是"数据库事务和消息发送无法原子"这个
经典问题，不是性能问题。

## 幂等的三件套（优先级从高到低）

MQ 是 **at-least-once**——重复投递是**必然事件**，不是意外（重试、consumer 重启、
网络分区都会造成）。所以消费侧必须幂等，而且**不能只靠一层**：

1. **写事实用唯一索引 + 看 `affectedRows`**
   `t_interaction` 的唯一键 `(user_id, kind, target_type, target_id)`。
   重复点赞 → 插入失败/影响 0 行 → 不产生新事件。这是最省的一层，在写入侧就掐掉了。
2. **消费侧 `t_consume_log(event_id, consumer)` 唯一索引**
   每个消费者一张去重记录。`eventId` 在写 outbox 时生成，**重投时保持不变**——
   如果重投时重新生成 id，这一层就完全失效。
3. **一切计数都有对账兜底**
   前两层都可能被绕过（手工改库、消费逻辑 bug、事件超过重试次数被丢弃）。
   对账是最后一道防线：用**事实表**重算，覆盖计数。

## 对账任务

| 项 | 值 |
|---|---|
| 触发 | Spring `@Scheduled`，每 10 分钟 |
| 输入 | `t_interaction` / `t_comment` 的**事实** |
| 输出 | 覆盖式写入 `like_count` / `favorite_count` / `comment_count` |
| 幂等 | 覆盖写，天然幂等 |
| 范围 | 只处理近期可能被读到的热点（P3 阶段数据量小，全量即可） |

P7 会换成 XXL-Job（多实例、可观测）。P3 单实例 + `@Scheduled` 足够，
过早引入调度中心只是增加部署面。

## 强一致的代价：一致性检查本身要能跑

`verify-p3.sh` 的 L4 必须能证明三件事，否则这套机制只是"设计上正确"：

1. **kill content-service → 点赞仍然成功，计数不变 → 重启 → 对账修回**
   （证明写路径不依赖 content 的可用性）
2. **手动重投同一事件 → 计数只 +1**
   （证明幂等真的生效，而不是"恰好没重复"）
3. **把 `like_count` 改成错误值 → 跑对账 → 修回**
   （证明对账真的在用事实表重算，而不是把计数抄一遍）

## 明确不做的

- **不做分布式事务**（Seata 之类）：跨库强一致的成本远大于收益，而这些计数
  本来就是"可以慢 5 秒"的数据
- **不做事件版本化**：不兼容变更 = 新 topic，新旧并行
- **不给点赞做 Redis 计数**：那是 P5 的事，现在做等于同时维护两套真相
