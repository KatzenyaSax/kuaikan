# 不引入内部签名，也不做隐式身份传播

网关是唯一信任源，向下游注入 `X-User-Id` / `X-User-Roles`，下游无条件信任这两个头
（前提见 ADR 0003）。在此之上，我们评估过两种加固，**都决定不做**：

1. **内部 HMAC 签名**：网关签 `HMAC-SHA256(secret, userId|roles|timestamp)`，服务验签名 + 时间窗
2. **Feign 隐式身份传播**：服务调服务时自动把入站身份转发给下游

## 为什么不做内部签名

它防的是"有人能直连服务端口"。但这个威胁很窄：能连上容器端口的人，基本也能读容器
环境变量、直连 MySQL / Redis——绕过签名的成本近乎为零。真正有效的地方只有一处：
**能连端口但读不到密钥**，而这恰恰是最不可能发生的组合。

而它要防的真实风险——**意外暴露端口**——已经由三件事盖住：

- compose 里不声明 `ports:`
- `verify.sh` 的配置层断言（除 gateway 外声明 ports 就红）
- UFW + 云厂商安全组

代价却是每一天的：漏引 `kuaikan-common-web` 就静默失效、用 curl 调内部接口要现算签名、
签名自带 60 秒窗口会给长链路埋偶发 401。

## 为什么不做隐式身份传播

ADR 0005 已经决定"读路径由前端并发聚合、服务间不做同步编排"，所以服务间同步调用本来
就该少。剩下的内部调用是**业务对业务**，不是**用户对业务**：

```
content-service 问 community-service：这个社群的成员列表
  → GET /internal/memberships?communityId=1&userIds=1,2,3
```

身份应该作为**显式参数**传进去，而不是依赖隐式上下文。显式参数更明确、更好调试，
不需要任何额外机制，而且可检查——内部接口里不应该出现 `UserContext`。

## Consequences

- **`UserContext` 只在"用户直接请求的服务"里有效。** 一旦发生服务间调用，身份作为参数传，
  不靠 header。这条是判断内部接口写法的依据。
- **内网直连可以伪造 `X-User-Id`**，这是明确接受的代价，由"端口不暴露"承担。
  `verify.sh` 的配置层断言就是这条代价的执行者。
- 若将来把中间件拆到多台机器、引入第三方服务、或出现需要跨越多跳的长链路，
  **需要重新评估，且应优先考虑网络层方案（mTLS / 服务网格），而不是应用层签名**。
- 这两套机制曾短暂实现并验证可用（含常量时间比较、60 秒时间窗、Feign 拦截器），
  后按上述理由移除。保留这段记录是为了避免后人重复讨论同一个问题。
