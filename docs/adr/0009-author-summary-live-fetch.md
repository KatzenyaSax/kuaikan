# 作者信息实时拉取，不在内容表里存快照

帖子与评论需要显示作者的昵称和头像。两种做法：

1. **快照**：`t_post` 里冗余存 `author_nickname` / `author_avatar`，发帖时写入
2. **实时拉取**：内容表只存 `author_id`，前端用批量接口现取

**选 2。** 并且这个选择推翻了 `architecture.md` 里"帖子详情返回正文 + 作者摘要 + 计数快照"
的原始表述，那句话倾向的是方案 1。

## 决定性理由：写路径的可用性

方案 1 要求 `content-service` 在**发帖**时拿到作者昵称，而昵称只存在 `user-service` 里。
于是发帖这条写路径变成：

```
content-service ──同步调用──> user-service     ← 发帖成功与否取决于 user-service 是否活着
```

这意味着 **user-service 挂掉时全站没人能发帖**。对一个以微服务架构为展示点的项目，
写路径依赖另一个服务的同步可用性，是最容易被指着说的地方；而且它和 ADR 0005
（服务间不做同步编排）方向相反。

方案 2 下 `content-service` 的写路径**只碰自己的库**，`author_id` 来自网关注入的
`UserContext`，没有任何跨服务依赖。

## 其他理由

**改昵称的即时性。** 刚做完 P1.6 的资料编辑。方案 1 下用户改完昵称，历史帖子仍显示旧昵称——
产品上会被当成 bug 报上来。方案 2 立即全站生效。

**评论会放大这个问题。** P3 的评论列表一屏 30 条评论可能来自 25 个不同作者。
方案 1 要 25 份快照，方案 2 复用同一个批量接口一次拿完。

**方案 1 省下的只有一次并行请求。** 前端本来就是并行请求（ADR 0005），
多一路 `GET /api/user/users?ids=` 不会增加感知延迟，而它是可缓存的 GET。

## 代价与约束

- **新增一个公网可见的读接口**：`GET /api/user/users?ids=1,2,3`（游客可读，因为是公开信息）。
  这是新增的攻击面，必须严格限定返回字段：
  **只返回 `userId` / `nickname` / `avatarUrl`**，绝不返回 `email`、`status`、`created_at`。
  网关白名单要为此单开一条精确条目，不能借用 `/ping/**` 那种前缀通配。
- **批量上限 100**，超过返回参数错误，防止被当成拖库接口。
- **前端必须在两路都到齐后再渲染**，否则作者名会闪一下。用 React Query 的并行 query +
  合并态处理，不做"先渲染作者占位再补"。
- **不缓存用户摘要**（P2 阶段）。等 P2 之后加 L1/L2 缓存时，**改昵称必须触发失效**——
  这是实时拉取方案唯一的额外义务。

## Consequences

- `t_post` / `t_comment` **不包含任何作者信息列**，只有 `author_id`。
- 帖子详情/列表的响应里只有 `authorId`，作者昵称头像由前端另行获取。
- 这也意味着**"消息是自包含快照"这条原则只适用于 notification 的消息**，
  不适用于帖子与评论。二者不要混为一谈：消息是"某人在某个时刻做了某事"的历史记录，
  帖子是"这篇内容现在长什么样"的当前状态。
