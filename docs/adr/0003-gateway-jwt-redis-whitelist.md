# 鉴权集中在网关，凭证失效靠 Redis 白名单

`user-service` 用 RS256 签发 access token（2 小时）与 refresh token（30 天，每次刷新轮换），公钥经 JWKS 端点暴露。网关是唯一验签点：验签 → 查 Redis 白名单 `auth:session:{jti}` → 向下游注入 `X-User-Id` / `X-User-Roles`。下游服务不再解析 token，只从 header 构造认证上下文。理由是论坛必须具备**登出、踢下线、封禁**三种即时失效能力：纯无状态 JWT 只能等过期，有状态 Session 则会牺牲水平扩展与读缓存空间。

## 前提与它的代价

「下游无条件信任 `X-User-Id`」这条设计的**唯一物理前提**是：服务端口不可从外部到达。
一旦某个服务端口泄漏（哪怕只是调试时临时加了一行 `ports:`），任何人都能伪造
`X-User-Id` 冒充任意用户——而且**完全静默**：系统照常工作，没有任何报错。

实测过这个失败态：修 B 方案之前，从容器网络直连 user-service 并只带一个
`X-User-Id` 头，就能拿到该用户的完整资料。

因此本 ADR 之后补了一层**应用级**防线（见下），而不是只依赖网络隔离：

```
gateway  →  X-User-Id / X-User-Roles
            X-Internal-Timestamp  = epoch 秒
            X-Internal-Signature  = HMAC-SHA256(secret, userId|roles|timestamp)
service  →  验签名 + 60 秒时间窗，过了才认 X-User-Id
```

这不是"再验一次用户凭证"（那是网关的职责，也是单点验签的意义所在），
而是回答一个更窄的问题：**这段 header 是网关写的吗**。

## Consequences

- **硬约束**：所有后端服务只能绑定内网地址或 Docker 网络，公网仅暴露 Nginx 的 443。一旦某个服务端口直接暴露到公网，任何人都能伪造 `X-User-Id` 冒充任意用户。
- 三种失效的路径互不重叠：登出删单个 `jti`；踢下线删该用户全部 `jti`；封禁同时改用户状态、清空全部 `jti`、并在登录接口拒绝。
- 游客可读的接口在网关放行名单中显式列出，不得依赖"忘记加鉴权"来放行。
- refresh token 轮换使旧的 refresh 立即作废，可作为异地登录检测的抓手。
- **密钥缺失时服务启动即失败**：内部签名是安全控件，不允许静默降级成"不校验"。
  宁可服务起不来，也不要起一个任何人都能伪造身份的服务。
- 内部签名密钥是网关与 7 个服务共享的，**泄漏后同样可伪造**。它的价值是
  "端口泄漏 / 网络被突破"这一层，不是"密钥泄漏"。密钥轮换需要重启两侧。
- 服务间调用（Feign）目前不传身份头，因此下游视为匿名。P3 需要传身份时，
  必须加 Feign 拦截器转发身份与签名，不能只转 `X-User-Id`。
