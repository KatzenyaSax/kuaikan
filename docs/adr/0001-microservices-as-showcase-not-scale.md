# 微服务是展示目标，不是扩展需求

项目定位为面向求职的技术展示，同时刻意接轨国内大厂生产形态。容量基线为**万级注册用户、峰值并发 50 以内**（见 `docs/project.md`）。因此采用微服务与完整中间件栈，是为了展示分布式设计能力与生产级工程实践，而非应对流量。取舍原则：**允许为学习与展示价值支付冗余成本，不允许为虚构的容量支付成本**——即可以上 K8s、可以铺完整可观测性，但不可以做分库分表、不可以做多可用区。

## Considered Options

- **模块化单体**：工程上更合理，代价是失去作品集价值，无法展示分布式一致性与消息中间件实践。
- **按真实规模的精简微服务**：更省力，但无法覆盖用户期望接触的大厂中间件体系。

## Consequences

- 服务数量仍需克制，每个服务都要能说清"为什么它不该和别人在一起"。
- 所有服务必须能独立启动；开发期用 Docker Compose 一键拉起全套。
- 中间件按"真实生产配置"搭（持久化、监控、必要的高可用开关），但按单机资源规划；**不为高可用搭真正的集群**（Redis/MySQL/RocketMQ 均为单实例或主从，见 `docs/project.md`）。
