# 部署：全组件云端容器化，只有一套环境

8 个 Java 服务与全部中间件全部以容器运行在**同一台境外云服务器**上。不存在本地运行环境，也不存在开发/测试/生产多套环境——**只有一套**。开发回路是：改代码 → 在服务器上重建受影响服务的镜像 → 重启该容器。

选择单环境而非"本地中间件 + IDE 跑服务"，是因为后者需要额外维护三条隔离规则（Nacos namespace 隔离、RocketMQ topic 隔离、XXL-Job 执行器隔离），任何一条漏掉都会让本地调试直接污染线上数据。由单人维护时，多环境带来的认知成本高于它省下的构建时间。

## Considered Options

- **服务在 IDE 跑 + 中间件容器**：迭代最快，但需要上述三条隔离规则，且环境形态与交付物不一致。
- **本地 + 云端双环境**：要维护两套 compose 与两条数据链，且两边数据永远对不齐。
- **一开始就上 K8s**：会在写出业务代码之前吃掉两到三周。

## Consequences

- **构建必须在服务器（x86_64）或 CI 上完成。** 开发机是 Apple Silicon（arm64），本地 `docker build` 产出的镜像在服务器上会直接 `exec format error`。**禁止在 Mac 上构建后推送。**
- 迭代粒度是单个服务：`docker compose up -d --build content-service`。用 BuildKit 的 `--mount=type=cache,target=/root/.m2` 持久化 Maven 依赖层，首次构建约 5~8 分钟，之后 30~90 秒。
- 服务器同时承担构建与运行，构建峰值会挤占服务内存；必要时加 swap 或限制构建并发。
- **没有预发环境，任何改动直接作用于唯一环境。** 因此数据库变更必须向后兼容（先加列、后使用、不删列），且**必须保留上一版镜像 tag 以便回滚**——这是单环境唯一的兜底手段。
- 没有 CI 门禁，改为"构建即验证"：镜像构建成功 + 容器启动 + healthcheck 通过，才算一次改动完成。
- 服务器选境外（香港）以规避 ICP 备案对上线时间的阻塞，代价是 50~100ms 额外网络延迟，在本容量下不可观测。
- 全量栈常驻内存约 9.5GB（含 ES 与 SkyWalking），机器低于 8C16G 会 OOM；一期不启 ES + SkyWalking 可降到 8C8G。
- Compose 的 profile 分组（`core` / `app` / `observe` / `extra`）是分阶段拉起全套的唯一入口。
- 编排升级到单节点 k3s + Helm 保留为**可选**阶段（P7 之后），不是上线前置条件；单环境下它的收益主要是学习与写法经验，若与交付时间冲突，砍掉它不影响任何功能。
