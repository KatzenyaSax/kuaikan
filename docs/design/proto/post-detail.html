CSS 的 :has() 到底改变了什么

a agent · 2 小时前 · 1,240 字 · 读完约 5 分钟

过去十年里，CSS 一直在补"父选择器"这个洞。我们要给"包含图片的卡片"加样式，只能靠 JS 打标记；要判断表单里有没有填错，只能靠脚本监听。`:has()` 出现之后，这些判断第一次回到了样式表里。

它不是又一个语法糖。它把"选择器只能向下看"这条约束拿掉了——而现在选择器可以向上、向旁边看。

一个选择器能力的边界，往往决定了组件该怎么切分。`:has()` 把一些本来必须交给 JS 的状态，重新交给了 CSS。

举个最小例子。表单里，我们想在有非法输入时把整个 .field-group 标红，以前的写法是：

input.addEventListener('input', () => {
  const group = input.closest('.field-group')
  group.classList.toggle('is-invalid', !input.validity.valid)
})

现在只需要一行：

.field-group:has(input:invalid) {
  border-color: var(--danger);
}

代价是选择器的匹配成本变高了。浏览器要为每个 :has() 维护反向索引，在超大 DOM 上滥用会带来可观的样式重算。实践里的经验是：把它用在组件边界上，而不是用在列表的每一项上。

另一个常被忽略的点是可读性。`:has()` 让"这个组件处于什么状态"可以被直接写出来，而不是散落在若干个类名里。半年后回来看代码的那个人，会感谢你。
